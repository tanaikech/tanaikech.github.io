Introduction

In my previous article, “Zero-Output-Token AI in Google Apps Script with Gemini Decisions API” Ref (source repository Ref), I demonstrated how Google DeepMind’s Gemini Decisions API (POST https://generativelanguage.googleapis.com/v1beta/decisions, powered by gemini-decision-1) Ref fits Google Workspace automation—covering Gmail inbox labeling, model cascade routing, and a Google Sheets PDF compliance audit. Among those examples, the PDF compliance audit drew an especially strong response, and I received inquiries about it from readers across many different fields.

The origin of that idea was actually very personal: before turning it into a Google Sheets demo, I had been using the Decisions API in my own daily writing workflow to check my own research papers, technical articles, manuscripts, and drafts against a self-defined set of review criteria all at once, surfacing issues instantaneously. When developers first encounter a classification endpoint like the Decisions API, the natural mental model is “Many-Inputs × Few-Labels”—classifying a stream of emails or support tickets into three to five categories. Flipping that geometry to “1-Input × up to 1,000-Criteria”—sending one rich multimodal artifact (a PDF, research paper, article manuscript, or ad creative) once and evaluating it against up to 1,000 independent questions in a single forward pass—turned out to be a usage pattern that most users had never envisioned.

Because of that response, I decided to write this dedicated follow-up article focused exclusively on this technique, which I refer to as Zero-Output Multimodal Auditing (ZOMA). Because gemini-decision-1 evaluates all questions against the shared input simultaneously without autoregressive text decoding Ref, ZOMA produces strictly zero output tokens ($0.00 output cost, with input tokens billed once at $0.10 per 1M input tokens) Ref while returning calibrated probabilities (0.01 to 0.99), discrete choices, and ordinal rubric scores (0–4). Moving beyond Google Apps Script into a universal, dependency-light Python 3 CLI published at gemini-decisions-api-python Ref, this article presents a reusable ZOMA auditing and weighted-scoring architecture and validates it across five live multimodal use cases (83 total criteria across Markdown, PDF, and PNG inputs). While I designed the core scenario and evaluation criteria for each of the five use cases myself, the sample input documents used to demonstrate and reproduce each run were generated with Gemini via samples/generate_samples.py Ref so that anyone can reproduce every benchmark without proprietary files; every latency, token count, probability, score, and cost figure reported in this article comes directly from live API runs, and you can immediately swap in your own local files and custom checklists.

In Plain English: What Is ZOMA?

Imagine handing a 20-page vendor contract, a research manuscript draft, an advertising banner, a student essay, or a grant proposal to a meticulous reviewer along with a structured checklist—and receiving every checkbox verdict, every 0–4 quality rating, and a clear flag on any ambiguous clause that needs human judgment back in under one second, for a fraction of a cent. That is Zero-Output Multimodal Auditing (ZOMA). Instead of asking an AI chatbot to write long prose explanations one question at a time, ZOMA sends your document once, evaluates dozens or hundreds of independent checklist rules simultaneously, and lets deterministic Python code handle all final math and pass/fail decisions.

Key Terms in Plain English

  • Single Forward Pass & Zero Output Tokens: Standard AI chatbots generate answers one word (token) at a time, which adds latency and output billing. A single forward pass reads your document once and returns structured numeric answers directly, generating zero written text and zero output-token cost.
  • Calibrated Probability (0.01–0.99): A reliability-tuned percentage expressed from 0.01 (1% likely “Yes”) to 0.99 (99% likely “Yes”). When the model is genuinely unsure (for example, 0.72), the score sits in the middle instead of pretending to be 99% certain.
  • Question Types (noul, choice, score): The three structured question formats supported by the Decisions API—noul for Yes/No checks, choice for picking one label from a fixed list, and score for rating quality on an ordered rubric such as 0 to 4.
  • OCR-Free Multimodal Input: Sending PDFs and images (like PNG banners) directly to the AI model as-is, without running a separate Optical Character Recognition (OCR) or PDF-to-text converter first.
  • CLI, JSON/YAML & Dry-Run: A Command-Line Interface (CLI) is a lightweight terminal program; JSON and YAML are plain-text formats used to write your checklist rules; and --dry-run checks your files and rules locally before making any paid API call.
  • Knock-Out Gate: A mandatory eligibility requirement (such as a maximum grant budget cap) where failing that single rule disqualifies a submission immediately, regardless of how high its overall quality score is.

1. Why Gemini Decisions API Excels at ZOMA & Architecture

Low latency and low cost are the most immediately visible advantages of gemini-decision-1, yet its deeper architectural strengths are what make Zero-Output Multimodal Auditing (ZOMA) production-grade across legal, editorial, visual, and academic domains Ref:

  • Sub-Second Single Forward-Pass Latency: Because the model evaluates all questions in a single prefill forward pass (reading the document once without generating text word-by-word) without autoregressive token-by-token decoding, end-to-end latency remains flat and sub-second (497.4–856.4 ms live measured across 14–20 criteria) instead of scaling linearly with output length.
  • Ultra-Low Cost with Strictly Zero Output Tokens: Shared document input tokens are billed once at $0.10 per 1M input tokens Ref, while output and thinking tokens remain strictly 0 ($0.00 output cost), cutting input volume by over 92% compared to sequential per-criterion calls.
  • Mathematically Calibrated Probabilities & Native Confidence Gating: Unlike generative LLMs whose self-reported verbal confidence is often poorly calibrated, gemini-decision-1 returns statistically calibrated probabilities (0.01–0.99) and confidence scores, enabling reliable automated NEEDS_REVIEW escalation thresholds (such as 0.85).
  • Zero JSON Parse Failures & Closed-Set Schema Guarantees: Because no free-form text is decoded into JSON strings, malformed JSON, hallucinated enum values, and schema drift are structurally impossible across noul, choice (2–255 options), and score (2–255 ordered rubric tiers) primitives Ref.
  • High-Density Parallel Batching (Up to 1,000 Independent Questions): A single request evaluates up to 1,000 independent criteria against the exact same shared context without cross-question prompt contamination or attention degradation from massive compound instructions.
  • 262,144-Token Unified Multimodal Context (OCR-Free): A single shared input accepts up to 262,144 tokens (256K) across mixed modalities—text, JSON, PDFs, images, audio, and video Ref—allowing native inspection of multi-page PDFs and high-resolution ad creatives without external OCR or PDF-to-text pipelines.
  • High Reproducibility for Programmatic Control Flow: Without autoregressive sampling drift or variable thinking-token traces, probability outputs remain highly repeatable across runs, making gemini-decision-1 a dependable upstream signal provider for deterministic downstream software logic.

Separation of Concerns

A common problem in LLM-based evaluation pipelines is asking a single generative model to read a document, judge 20 criteria, apply custom business weights, check hard eligibility rules, and sum the final score in one autoregressive JSON response. When AI judgment and arithmetic are mixed together, models exhibit silent summation drift, inconsistent threshold enforcement, and brittle JSON formatting errors.

To prevent these problems by design, our Python CLI enforces a strict two-layer separation of concerns, illustrated in Figure 1.

Figure 1: Shifting from sequential autoregressive LLM loops to 1-Input × up to 1,000-Criteria evaluation with strict separation between gemini-decision-1 inference (client.py) and deterministic Python aggregation (evaluator.py).

As shown in Figure 1, the pipeline divides responsibility across three focused modules:

  • Stateless Multimodal Transport (cli/client.py) Ref: Reads a local .md, .txt, .pdf, .png, .jpg, .jpeg, or .webp file once, Base64-encodes binary documents and images natively without OCR middleware (packaging PDFs and images directly for the API without separate text-extraction tools), authenticates strictly via the x-goog-api-key HTTP header, automatically chunks checklists exceeding 1,000 questions into compliant batches, applies bounded exponential backoff on HTTP 429/5xx, and normalizes proto-JSON response fields into typed Python dictionaries.
  • Zero-Output-Token Semantic Inference (gemini-decision-1): Evaluates every criterion independently against the shared input in one forward pass, returning calibrated noul probabilities (0.01–0.99), choice probability distributions, or score expected values and ordinal bucket distributions—with 0 output tokens generated.
  • Deterministic Evaluation Engine (cli/evaluator.py) Ref: Operates completely offline with zero network I/O. It applies exact threshold rules, risk-flag inversions (expected: "no"), hard knock-out gates, weighted linear scaling, negative penalty deductions, and borderline/low-confidence escalation in pure Python—verified offline by the Stage-3 boundary stress test suite (an automated offline check that verifies the math handles edge cases like zero scores or borderline ties) cli/test_evaluator_stress.py Ref.

This decoupling guarantees that LLM arithmetic hallucination is structurally impossible: the AI model only produces calibrated per-criterion signals, while Python owns every threshold comparison, weighted sum, and pass/fail verdict. Table 1 compares the two deterministic operating modes built into evaluator.py alongside a traditional autoregressive LLM loop.

Table 1: Comparison of Naive Autoregressive LLM Loops vs. Gemini Decisions API Mode A (audit) and Mode B (weighted_scoring) across token scaling, output tokens, arithmetic determinism, and human-in-the-loop gating.

Table 1 highlights why a single checklist schema can drive two distinct enterprise patterns:

  • Mode A (audit): Designed for binary compliance, pre-flight linting, and risk scanning. Each noul criterion specifies expected: "yes" (required safeguard) or expected: "no" (prohibited risk flag). Any signal whose confidence falls below confidence_threshold (default 0.85, i.e., 0.15 < P < 0.85) is routed automatically to NEEDS_REVIEW rather than guessed. For choice criteria, explicit fail_choices or review_choices trigger FAIL or NEEDS_REVIEW; for score criteria, expected scores are gated against pass_min and fail_max.
  • Mode B (weighted_scoring): Designed for rubric grading, grant screening, and procurement scoring. Criteria can be marked as knockout: true (hard eligibility gates where a FAIL immediately disqualifies the submission regardless of points, and low confidence forces NEEDS_REVIEW), positive-weight noul or score dimensions (where an ordinal 0–4 score contributes (score / max_scale) * weight points), or negative-weight noul penalty flags. If the final total falls within ±borderline_margin of cutoff_score, or if too many items exhibit low confidence (max_low_conf_for_auto), the engine escalates the overall verdict to NEEDS_REVIEW.

3. Mode A Live Walkthrough & Empirical Results

Mode A (audit) targets high-precision defect detection across text, multi-page PDFs, and raw visual creatives. Following the three single-batch pipelines mapped in Figure 2, we examine each Mode A use case individually alongside its dedicated live test results infographic (Figure 4, Figure 5, and Figure 6).

How to read the live numbers in Sections 3 and 4:

  • Required checks (expected: "yes"): We want the document to contain this element, so a high probability (p >= 0.85) means PASS, while a very low probability (p <= 0.15) means FAIL (missing requirement).
  • Risk & defect flags (expected: "no"): We want this problem to be absent, so a low probability (p <= 0.15) means PASS (safe), while a high probability (p >= 0.85) means FAIL (risk or violation detected).
  • Human-review zone (0.15 < P < 0.85): Whenever the model’s confidence is below 0.85, the tool refuses to guess and routes that criterion to NEEDS_REVIEW for a human reviewer.
  • Rubric scores (0–4, e.g., 3.17 / 4): Rather than forcing a blunt whole number, the model returns a probability distribution across levels 0 through 4 and computes the weighted average (expected score) for fine-grained grading.

7. Limitations, Best Practices & Summary

While Zero-Output Multimodal Auditing (ZOMA) excels at high-throughput verification and structured scoring, treating it as a drop-in replacement for every generative workflow is a mistake. Five engineering principles keep production deployments reliable:

  • Pair Decisions API with a Reasoning Model When Explanations Are Required: Because gemini-decision-1 emits zero output tokens, it tells you which clauses failed (risk_uncapped_customer_indemnity: p = 0.973) and how confident it is, not how to redline the contract prose. The optimal production pattern is a two-stage cascade: run decisions_audit.py on 100% of incoming documents at ~$0.0003 each, and invoke a generative reasoning model only on the specific FAIL or NEEDS_REVIEW items that require written redlines or student feedback.
  • Embed ZOMA Directly Inside AI Agents (Antigravity, Claude, and Beyond): Because the tool is a stateless Python CLI with --format json output, agentic platforms like Antigravity and Claude can call cli/decisions_audit.py as an external quality gate during autonomous workflows—checking their own generated manuscripts, specs, or images against dozens of organization rules in under a second for roughly $0.0003, then fixing only the flagged FAIL or NEEDS_REVIEW items before handing the final output to a human.
  • Write Atomic, Observable Checklist Criteria: Compound questions (“Does the contract include SOC 2, AES-256, and 72-hour breach notice?”) blur probabilities when only two of three clauses are present. Splitting them into atomic noul criteria costs only a few extra question tokens per item while keeping calibrated probabilities sharp.
  • Tune Confidence Thresholds & Borderline Margins to Domain Risk: Defaulting to confidence_threshold = 0.85 works well for general pre-flight checks, as demonstrated by UC1 and UC2 catching ambiguous items automatically. For regulated legal or medical gates, raising the threshold to 0.90–0.95 widens the NEEDS_REVIEW safety band so borderline cases always reach human reviewers.
  • Respect the 1,000-Question Batch Boundary: Each POST /v1beta/decisions request accepts up to 1,000 questions Ref. Our client.py automatically chunks larger checklists into sequential 1,000-question batches while preserving the shared input, though keeping single-document checklists focused and non-redundant maximizes signal clarity.

Summary

Instead of asking an AI chatbot to read a file and write long answers one question at a time, Zero-Output Multimodal Auditing (ZOMA) sends one document, PDF, or image once to Google’s Gemini Decisions API (gemini-decision-1) Ref and checks up to 1,000 rules in a single pass—with zero text generated and exact, trustworthy results:

  • Under a Second and Almost Free to Run: Across all five live tests (83 checks across Markdown, PDF, and PNG files), every audit finished in under 1 second (average 732.6 ms), generated 0 output tokens, cut input tokens by 92.9%–95.0% compared to checking rules one by one, and cost $0.001526 in total—roughly 655 full five-document audits for a single US dollar.
  • Catches Real Problems Without Blindly Guessing (Mode A): On technical drafts, vendor contracts, and ad images, ZOMA reliably caught confidentiality leaks, risky legal clauses, and prohibited ad promises—and whenever a rule fell in a gray area, it automatically flagged NEEDS_REVIEW so a human could make the final call.
  • Exact, Math-Error-Free Grading and Screening (Mode B): On student case studies (86.17 / 100) and grant applications (91.40 / 100), the AI evaluates each rubric item while a simple Python script handles all additions, penalties, and mandatory eligibility rules—eliminating AI calculation mistakes completely.
  • Ready for Both Everyday Users and AI Agents: You can immediately run the same tool on your own local files and custom checklists without building OCR or complex code, and autonomous AI agents like Antigravity and Claude can call it directly as a fast, low-cost self-check before delivering finished work.
